# Localization (i18n)

enough. ships with English (`en`, default) and German (`de`). All
user-facing strings live in a single module — `src/i18n/translations.ts` —
so adding a language is a matter of adding one object with the same keys.

## File structure

```
src/i18n/
  index.ts          runtime: t(), setLang(), useLang(), getLang()
  translations.ts   dictionary objects keyed by language code
  __tests__/        i18n.test.mjs (interpolation + placeholder security)
```

The runtime API (`src/i18n/index.ts`):

- `t(key, params?)` — translate `key` in the current language, falling back
  to English when the current language does not define that key. Parameters
  replace `{name}` placeholders in a single left-to-right pass so parameter
  values can never be re-scanned as templates.
- `setLang(code)` / `getLang()` — switch and read the current language. The
  choice is persisted in `localStorage` (`enough-lang`).
- `useLang()` — React hook; re-renders the component subtree on language
  change so every `t()` call updates without a page reload.

## Adding a new language

1. Add a new top-level entry under `translations` in
   `src/i18n/translations.ts`. Use the two-letter ISO 639-1 language code as
   the key (e.g. `fr`, `es`, `nl`). Copy the English object as a starting
   point so the nesting structure is preserved.
2. Extend the `Lang` union type near the top of `translations.ts` to include
   the new code:
   ```ts
   export type Lang = 'en' | 'de' | 'fr';
   ```
3. Translate every leaf value. Leave the nesting (dot-paths) and the keys
   exactly as they are in English. Placeholders (`{email}`, `{username}`, …)
   must be preserved verbatim — you may reorder them, but the `{name}` token
   itself must appear in the translated string.
4. Add the language to the in-app language picker in
   `src/components/settings/LanguageSettings.tsx` (the `LANGUAGES` array maps
   codes to visible names). The auth-screen language switch reuses the same
   source automatically.
5. Add a language-switch entry in the auth chrome (`src/components/AuthChrome.tsx`)
   if the new language should be selectable from login/register as well.
6. Run the parity checker to confirm every key is present:
   ```sh
   npm run i18n:check
   ```
   The checker fails the build on any missing or orphan key.
7. Run the i18n test suite to verify interpolation still works:
   ```sh
   npm run test:i18n
   ```

## Invariants

- **No hard-coded user-facing strings.** Components must call `t('…')` (or
  pull a translated label via a typed variable). English/German text living
  directly in JSX is a bug.
- **Interpolation values are data.** The single-pass replacement in `t()`
  guarantees that content coming from a parameter value is never re-scanned
  for placeholders — even if a value legitimately contains `{…}`. Do not
  rewrite `t()` with sequential `split().join()` or any other strategy that
  iterates placeholder replacement over already-substituted output.
- **Fall back to English, never to the key.** If a translation is missing in
  the active language, `t()` falls back to the English string. The raw key is
  only returned when neither language has the string (which the parity
  checker prevents in CI).
- **Repository-level content stays English.** Comments, documentation, error
  messages and logs remain English per `docs/arena-instructions.md`. Only the
  values inside the translation objects are localized.

## Tests

- `npm run i18n:check` — parity check (every non-EN language covers every EN
  key; no orphan keys).
- `npm run test:i18n` — interpolation correctness, placeholder-safety (values
  cannot inject new placeholders), EN/DE string resolution, OTP C2 warning
  texts.
